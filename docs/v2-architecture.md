# Personal Dashboard V2 — техническая архитектура

Этот документ описывает устройство Personal Dashboard V2 в корне самостоятельного репозитория. Цели проекта — в [концепции](v2-concept.md). Backend и frontend V2 пишутся с нуля, без переноса кода текущего Dashboard.

## Состав системы и границы

- Один ASP.NET Core host и один solution: **модульный монолит** на C# с PostgreSQL и EF Core.
- Серверные модули: `Knowledge`, `Planning`, `Tasks`, `Chat`, `Agent`, `Search`. У каждого одинаковые слои `Domain`, `Application`, `Infrastructure`, `API`, включая небольшие модули.
- `Domain` хранит сущности и правила; `Application` — команды, запросы и обработчики; `Infrastructure` реализует хранение и внешние адаптеры; `API` переводит HTTP-запросы в use cases. Путь: `API → Command/Query → Handler → Repository → PostgreSQL`. Диспетчер — MediatR или аналог.
- Зависимости направлены к Domain и Application. Инфраструктура реализует их интерфейсы. Host собирает модули; они обращаются друг к другу через межмодульные контракты, не меняя чужие таблицы напрямую.
- Общие технические службы: соединение с БД, логирование, AI-провайдеры и синхронизация. На первом этапе авторизации нет; доступ к серверу предполагается через доверенную сеть.

## Организация репозитория и solution

V2 живёт в корне этого самостоятельного репозитория. Предлагаемая структура:

```text
PersonalDashboard.V2.slnx
backend/
  src/
    Host/                 PersonalDashboard.V2.Host.csproj
    Contracts/            PersonalDashboard.V2.Contracts.csproj
    Platform/             PersonalDashboard.V2.Platform.csproj
    Modules/
      Knowledge/
        Domain/           PersonalDashboard.V2.Knowledge.Domain.csproj
        Application/      PersonalDashboard.V2.Knowledge.Application.csproj
        Infrastructure/   PersonalDashboard.V2.Knowledge.Infrastructure.csproj
        Api/              PersonalDashboard.V2.Knowledge.Api.csproj
      Planning/           те же четыре проекта
      Tasks/              те же четыре проекта
      Chat/               те же четыре проекта
      Agent/              те же четыре проекта
      Search/             те же четыре проекта
  tests/                  модульные и интеграционные тестовые проекты
frontend/                 один Vue-проект
  src/app/                оболочка, маршруты, навигация
  src/modules/            knowledge, planning, tasks, chat, search
  src/shared/             UI-компоненты и общие клиентские контракты
  src/offline/            IndexedDB и Sync Engine
```

`Host` — точка запуска: конфигурация, DI, HTTP pipeline и подключение endpoints всех модулей. `Contracts` содержит только стабильные межмодульные интерфейсы, DTO и события, без доменной логики и EF Core. `Platform` реализует общую техническую инфраструктуру: подключение к PostgreSQL, логирование и транспорт синхронизации. Адаптеры AI-провайдеров принадлежат `Agent.Infrastructure`; поисковый индекс — `Search.Infrastructure`.

Правила ссылок между проектами: `Domain` не зависит от других проектов V2; `Application → Domain + Contracts`; `Infrastructure → Application + Domain + Contracts` и при необходимости `Platform`; `Api → Application + Contracts`; `Host → Api + Infrastructure + Platform`. Взаимодействие между модулями идёт через `Contracts`, а не через ссылки на чужие `Infrastructure` или общие таблицы. Контракты должны быть узкими и принадлежать конкретным операциям, чтобы общий проект не превратился во второй доменный слой.

| Модуль | Ответственность |
| --- | --- |
| `Knowledge` | Дерево разделов, документы, ручное редактирование. |
| `Planning` | Проекты, эпики, фичи, прогресс по фичам. |
| `Tasks` | Единые записи задач, Backlog/Сегодня, состояния и порядок. |
| `Chat` | Временные сессии, сообщения и показ предложений пользователю. |
| `Agent` | Оркестрация модели, инструментов и подтверждаемых действий. |
| `Search` | Индексация и единый гибридный поиск по рабочим разделам. |

## Данные и доменные правила

PostgreSQL — источник истины для рабочих данных. `Knowledge` владеет деревом разделов и Markdown-документами. `Planning` — проектами, эпиками, фичами и их состоянием. `Tasks` — задачами, разделами и рабочими состояниями. Активные сессии `Chat` живут в памяти процесса; переписка и неподтверждённые предложения не записываются в PostgreSQL. Search хранит только производный индекс, который можно пересоздать из доменных данных.

Задача планирования и задачника — **одна запись**, принадлежащая Tasks. Связь с проектом, эпиком и фичей задаётся идентификаторами и проверяется через контракт Planning. Положение задачи: `planned`, `backlog`, `today`, `archived`; состояние работы в Today: `new`, `in_progress`, `done`. Перенос в Backlog и обратно меняет положение, сохраняя связь. Задачи без проекта допустимы.

Завершённость фичи задаётся явно. Прогресс эпика — доля завершённых фич в процентах; прогресс проекта — среднее процентов всех его эпиков с одинаковым весом. Пустой эпик даёт 0% и участвует в среднем; проект без эпиков даёт 0%. На каждом уровне результат округляется до целого процента, половина — вверх. Количество и статус задач не меняют прогресс автоматически. Фронтенд рассчитывает те же показатели из текущего дерева, в том числе для сохранённых данных и локальных изменений без сети. Технические имена `Milestone`, `milestoneId` и маршруты `milestones` сохранены для совместимости API, БД и офлайн-очереди; пользовательское название — «Эпик». Достоверный прогноз сроков потребует отдельной модели оценок и фактического темпа.

## Search

Изменения документов, планов и задач обновляют поисковые представления. Для длинных текстов хранятся фрагменты с идентификатором исходного объекта, путём и версией. Переписки не индексируются. Основные сущности остаются обычными записями PostgreSQL; embeddings — дополнительный индекс через `pgvector`.

Поисковый запрос сочетает:

1. Точные слова, части слов и PostgreSQL Full Text Search.
2. Поиск близких по смыслу фрагментов через embeddings.
3. Объединение и устранение дублей, ранжирование и при необходимости отдельный reranker.
4. Чтение исходного объекта или соседнего контекста, если фрагмента недостаточно.

Search даёт один инструмент и для UI, и для Agent; модель не выбирает сама между текстовым и векторным поиском. Запросы «найди всё» не ограничиваются слепо несколькими top results: полнота и ссылки на источники проверяются отдельно. Минимальный контрольный случай — оба документа с упоминаниями декора должны попасть в результат и ответ. Для точных подсчётов Agent использует структурированные запросы доменных модулей.

В чате сервер задаёт область поиска по области текущей сессии. Для планирования в неё входят проекты, эпики, фичи и задачи с привязкой к фиче; фильтр задач применяется до ранжирования и ограничения выдачи. Прошлые переписки не являются источником поиска.

## Chat, Agent и подтверждение

`Chat` держит текущую переписку в памяти и отображает сообщения, ответы и предложения; `Agent` управляет моделью, поиском и инструментами. При выходе из чата сессия и неподтверждённый черновик удаляются. Повторный вход открывает чистый чат. Для оборванных соединений действует срок бездействия 30 минут. Подтверждённые документы и задачи сохраняются независимо от сессии. Существующие записи старого механизма истории не удаляются этой доработкой, но активный чат их не восстанавливает.

Область сессии фиксируется на сервере при создании: `knowledge`, `tasks`, `planning` или `general`. Кнопка чата в рабочем разделе передаёт соответствующую область. В базе знаний доступны документы и разделы, в задачнике — задачи, в планировании — план и связанные с фичами задачи. Общий чат может обращаться ко всем рабочим разделам. Смена области начинает новую сессию. Модель получает только соответствующие инструменты, а сервер отдельно проверяет поиск, чтение, подготовку и подтверждение действий. Фокус `entity` дополняет область конкретным объектом и не расширяет её.

Agent не получает прямого доступа к БД. Его типизированные инструменты вызывают Application-контракты модулей с той же проверкой, что и ручные API. Чтение и поиск выполняются сразу. Любое изменение проходит схему `намерение → структурированное предложение → предпросмотр → подтверждение → выполнение`:

- Предложение фиксирует тип операции, конкретные ID, новые значения и ожидаемые версии объектов. UI формирует понятный шаблон по этой структуре; модель не выполняет запись при подготовке текста.
- Текущий сценарий готовит создание одного документа или одной задачи. Кнопка ясно обозначает, какое действие подтверждает; доменная запись выполняется в транзакции.
- Уточнение создаёт новый предпросмотр. Обычный вопрос сохраняет ожидающий черновик; уход из чата удаляет его. Без кнопки подтверждения данные не меняются.
- При подтверждении backend выполняет **именно показанные** действия и повторно проверяет версии и бизнес-правила. Устаревшее предложение не применяется: пользователь получает актуальный предпросмотр. Повторный клик не должен создавать повторную операцию.

Переписка позволяет исправлять ожидающее предложение до сохранения. Изоляция областей не добавляет новые операции редактирования уже сохранённых записей. Подтверждение, замена черновика и закрытие сессии согласованы через один механизм последовательного доступа; предложение отмечается применённым после успешного завершения доменной транзакции.

Основная модель — локальная Gemma 4 через заменяемый AI-адаптер. Backend проверяет формат вызовов, параметры и результат; при обнаруживаемой неудаче может повторить запрос и перейти к более сильной модели, например DeepSeek. Содержательную неполноту ответа нельзя всегда распознать автоматически: качество Gemma и критерии fallback проверяются на наборе реальных вопросов. Условия передачи личных фрагментов облачному провайдеру нужно определить отдельно.

Каждый запрос чата передаёт явно выбранную модель: Gemma по умолчанию или DeepSeek после переключения пользователем. Ручной выбор DeepSeek и автоматический fallback с Gemma различаются в данных обращения, чтобы история показывала, какой моделью был получен ответ.

## Frontend

Один Vue frontend с общей оболочкой, маршрутизацией, дизайн-системой, глобальным чатом, поиском и синхронизацией. `knowledge`, `planning` и `tasks` — отдельные frontend-модули со своими страницами, компонентами, состоянием, маршрутами и API-клиентами. Их связь с общей оболочкой идёт через явные контракты.

Шапка чата показывает область текущей сессии. Переход в общий чат открывает новую пустую сессию. Идентификатор разговора не сохраняется в URL для последующего восстановления. Выход, новый чат и смена области очищают сообщения и отправляют запрос удаления сессии; при аварийном закрытии помогает серверный срок бездействия.

Переключатель модели расположен в шапке чата во всех точках входа; начальное значение — Gemma, второе — DeepSeek. Выбор влияет на следующий запрос и остаётся видимым пользователю.

Интерфейс включает desktop sidebar, мобильную нижнюю навигацию, дерево знаний, иерархию плана, Backlog/Сегодня, экран чата, контекстные меню и режим сортировки; поведение реализовано в Vue-модулях.

## Offline и синхронизация

Frontend — PWA. Статические ресурсы доступны после установки; IndexedDB хранит локальную копию данных и очередь ручных операций. UI читает локальные данные и позволяет менять их без сети. Общий Sync Engine передаёт очередь серверу и получает изменения **по сущностям и версиям**, а не заменяет всё хранилище одним snapshot. Нужны обнаружение конфликтов и корректное отражение удалений; точную политику разрешения конфликтов следует определить до реализации Sync Engine.

Операции, пришедшие из offline-очереди, повторно проходят серверные проверки. AI-чат требует доступного провайдера и не является условием ручной offline-работы. Позже тот же Vue frontend можно упаковать в Android через Capacitor, скрыв локальное хранилище за адаптером.

## Границы реализации

Память внешних агентов в V2 отсутствует. Автоматическая передача помеченных задач агентам — возможная V3. Импорт существующих JSON-данных, если потребуется, должен быть отдельной проверяемой операцией; работа V2 не зависит от хранилища старого Dashboard.
